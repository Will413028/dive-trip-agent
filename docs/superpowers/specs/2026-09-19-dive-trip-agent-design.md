# 潛旅規劃 Agent — 第一版設計

本文件描述產品設計與驗收目標，不代表真模型品質或公開部署已通過；最新狀態見 [release evidence](../../release-evidence.md)。
工作名稱：Dive Trip Agent；不是正式品牌名稱。

## 1. 產品目標

建立可公開操作的獨立 Web demo，讓潛在委託者親自體驗：從模糊需求出發，透過對話與直接操作，完成可修改、鎖定、復原及分享的潛旅行程。

這不是單純旅遊問答，也不是旅行社或潛水安全決策系統。作品要證明「LLM 能理解變動需求，而軟體能可靠地執行與保存結果」。尚未驗證市場需求，不把作品展示等同商業產品成立。

本產品的程式、資料、帳號與部署獨立，不先建共用 Agent 平台，不使用其他專案或未獲授權的資料。公開範例使用去識別化的離線 regression vectors；原始 claims、reports、usage 留於 ignored local storage，不從公開 fixture 重設模型 quota。

## 2. 第一版使用者與成功情境

使用者包括試用作品的潛在客戶，以及想探索行程安排的休閒潛旅者。前者不必具有潛水知識，也不必註冊就能體驗。

主要展示情境：

> 兩個人想安排四天潛旅，一個人不潛水，希望住舒服一點。

流程：輸入需求 → 確認缺少的關鍵條件 → 比較目的地 → 選擇方案 → 建立行程 → 鎖定住宿並調整預算／活動 → 檢視差異 → 套用 → 復原／儲存／分享。

第一版內容範圍為小琉球、綠島、墾丁。這是資料集範圍，不代表對任何人的適合度或安全背書。每次行程只選一個目的地，不做跨目的地交通最佳化。

初始產品限制：1–6 位旅客、2–7 天、以 TWD 顯示預算；超出範圍明確提示，不偷偷截斷需求。

## 3. 方案取捨

採「精選資料的互動規劃型」，不採第一版全網即時探索：

- 精選資料型較易驗證来源、重現展示與控制費用；代價是目的地和活動有限。
- 即時探索型範圍廣，但外部服務、資訊新鮮度、價格與可訂狀態的不確定性會壓過核心互動。

採單一 Agent 搭配明確工具，不使用多 Agent。LLM 理解需求、提問與產生候選修改；程式負責權限、條件檢查、價格計算、資料引用與版本套用。即使模型說已完成，也只有資料庫成功提交後才能顯示完成。

## 4. 畫面與互動

桌面左側為對話，右側為行程工作台；手機切換對話／行程，保留未送出的輸入與操作狀態。

工作台包含需求卡、目的地比較、每日活動卡、地圖標記、預算明細與修改提案。地圖只呈現可驗證的地點座標，不畫出未經路線服務驗證的交通路線，也不假造交通時間。

卡片和聊天修改同一個結構化行程。拖曳排序不列第一版；先提供移動到指定日期、替換、移除、鎖定等明確操作，降低行動版與無障礙操作成本。

### 4.1 需求確認

以人數、潛水／非潛水人數、天數或日期、預算範圍、住宿偏好與行程步調為主。資訊不足只詢問影響下一步的條件。

日期未定仍可規劃，但畫面標「日期未定」；不產出天氣、開放時間、價格或可訂狀態的當日保證。潛水經驗屬使用者自述，不作為系統核發資格的依據。

### 4.2 鎖定與局部修改

住宿或活動鎖定後，該項的內容、日期與費用依據都不能被 Agent 改掉。需要移動或替換時，要求使用者先解鎖；不能藉移除父日期或改總天數繞過鎖定。

「第二天下午留白」只移除或調整該時段受影響的項目。若連帶影響其他日期、共同活動或交通安排，差異提案必須顯示所有受影響項目。

改人數後重新計算按人、按房或固定費用；若鎖定住宿的已知容納條件不足，產生衝突而不是換住宿。

### 4.3 差異與套用

每個提案顯示新增、移除、修改、費用差異、保留的鎖定項目及未解決問題。使用者明確接受後才更新行程；取消提案不改動既有行程。

提案生成後如有人先改行程，原提案變為過期，必須依最新版本重算；不靜默覆蓋較新內容。

### 4.4 復原與接續

復原建立一個內容等同舊版的新版本，不刪歷史。地圖、活動、條件、鎖定與預算一併還原；對話紀錄保留並顯示復原事件。

重新整理以資料庫最後成功保存的狀態為準。若模型執行中斷，不聲稱仍在背景執行；顯示中斷與重試。第一版不保證跨裝置恢復匿名編輯權限。

## 5. 資料、來源與預算

目的地和活動採人工整理的結構化目錄。每筆資料保存來源網址、查核時間、事實／示範分類；使用授權圖片或自製視覺素材。正文內容來自外部時一律當不可信資料，不當作 Agent 指令。

每項費用有計價單位（每人／每房每晚／整團固定）、整數最小貨幣單位、數量、來源及估算／示範標記。數量與加總由程式計算，不採用模型輸出的總價。

未知費用使用 null 與原因，不當成零。若存在未知項，顯示「已知項目小計＋待確認費用」，不能宣稱全程在預算內。明列不包含的交通、裝備、餐飲等項目；不要把缺少資料誤呈現為免費。

真實目的地資訊與虛構住宿／活動必須分開標示。示範價格不能暗示真實業者報價、空房、船班或預約名額。

公開上線前需逐筆核對使用到的真實資料；本設計文件沒有驗證現行船班、價格、業者政策或潛水條件。

## 6. 架構與責任

技術方向為 Next.js、TypeScript、PostgreSQL。實作開工時查核官方文件並選擇當時受支援的版本，再固定 lockfile；本文件不捏造已安裝的版本或相依性。

| 模組 | 責任 | 禁止事項 |
|---|---|---|
| Web 工作台 | 顯示結構化狀態、收集操作、差異確認 | 不自行另存一份相互矛盾的行程 |
| Agent runner | 理解需求、呼叫工具、回傳結構化提案 | 不直接任意更新資料庫、不執行外部指令 |
| Catalog | 查詢有來源的目的地、活動與費用資料 | 不把查無結果替換成模型杜撰 |
| Domain services | 驗證鎖定／條件、計算費用、產生差異 | 不依賴自然語言判定權限或金額 |
| Persistence | 版本、提案、執行狀態、冪等請求 | 不允許過期版本覆盖 |
| Sharing | 經確認的唯讀快照、撤銷 | 不暴露對話與匿名編輯憑證 |

工具只暴露必要操作：查目的地、查活動、試算預算、驗證提案。儲存與分享由應用服務在使用者操作後執行，不因模型呼叫就自動公開內容。

模型供應商、模型名稱、地圖供應商與部署服務屬實作前的環境選型，不影響本設計的資料契約。首個開發階段需查官方文件、可用帳號及成本後記錄選型；不能擅自開付費服務或輸出秘密值。

### 6.1 核心資料

- Trip：擁有者 session、目前版本、建立與更新時間。
- TripVersion：不可變完整快照，包括需求、活動、鎖定、費用與引用來源。
- Proposal：tripId、baseVersion、結構化修改、驗證結果、狀態；狀態為 pending／applied／rejected／stale。
- AgentRun：requestId、狀態、已完成工具事件、錯誤類型、用量；狀態為 running／succeeded／failed／interrupted。
- ConversationMessage：使用者與助理訊息；不保存或展示模型內部思考。
- ShareSnapshot：經使用者確認的脫敏行程快照、不可猜測的存取 token、撤銷狀態。

套用交易同時驗證所有權、baseVersion、proposal 狀態與 requestId，再保存新版本並切換目前版本。requestId 重送回傳同一結果；不同請求套用過期版本回傳衝突，不重複寫入。

### 6.2 執行狀態

畫面依真實工具事件顯示查詢中、計算中、待確認、已儲存或失敗。不用計時動畫假裝已完成查詢。

模型呼叫與工具有逾時及呼叫數上限。自動重試只限唯讀操作；寫入靠冪等與查詢已提交結果解決未知回應，不盲目重跑。

## 7. 公開 demo 邊界

匿名編輯權限使用 server-issued session 與 HttpOnly cookie；每次讀寫都驗所有權，不能只憑 tripId 修改。cookie 與同源檢查、請求驗證、服務端金鑰隔離在公開部署前驗收。

設定每個 session 的回合額度與全站每日用量上限；初始預設每個 session 每日 20 回合、每個回合最多 6 次工具呼叫、60 秒執行上限。全站金額上限以部署時使用者核准的實際預算設定，未設定則不開放公開 LLM 呼叫。另做 IP 層限速，不能把可重建 cookie 當唯一費用防線。

分享前預覽將公開的欄位。連結固定指向當時快照，後續編輯不自動公開；分享頁不包含私人對話、session、聯絡資訊或內部工具日誌。連結可撤銷、不提供編輯權、設定不索引，但提醒「持有連結者可讀」，不把 noindex 當保密機制。

匿名資料預設保存 30 天後清除，分享連結一併失效；畫面告知保存期限並提供刪除行程入口。記錄品質與成本所需的技術指標，避免在日誌複製完整私人輸入。

潛水安全、資格、健康狀況與當日是否下水交由教練／業者評估。系統只協助安排行程與整理待確認事項，不生成潛水剖面或安全背書；相關時間安排如未有已核對規則，標待業者確認，不宣稱整份計畫已通過安全驗證。

## 8. 第一版不做

- 真實預訂、付款、代寄訊息、查詢保證可訂名額。
- 全球目的地、跨目的地交通最佳化、無限制網路爬取。
- 多人同步編輯、正式會員與跨裝置帳號系統。
- 語音、多 Agent、共享平台、原生 app。
- 自動適潛判定、醫療或保險建議、取代教練的潛水安全決策。

## 9. 驗收矩陣

| 編號 | 情境 | 必須觀察到的結果 |
|---|---|---|
| A1 | 首次輸入模糊需求 | 收集必要條件並生成可操作方案；不強迫填無關資料 |
| A2 | 鎖住宿後降低預算 | 住宿與引用價格不被改寫；無解時解釋衝突 |
| A3 | 第二天下午留白 | 差異只包含受影響項；確認前不改原行程 |
| A4 | 兩人改四人 | 按人／房／固定費用重算；容量衝突顯式呈現 |
| A5 | 費用缺漏 | 顯示待確認與已知小計，不宣稱預算達標 |
| A6 | 提案生成後行程已更新 | 舊提案不能套用，要求重算 |
| A7 | 套用後網路斷線並重送 | 僅建立一個版本，回傳既有結果 |
| A8 | 復原 | 條件、鎖定、活動、地圖與費用一致還原 |
| A9 | 查詢／模型逾時 | 保留既有行程，顯示可理解錯誤與重試入口 |
| A10 | 重新整理 | 還原最後成功保存狀態；未完成執行不偽裝成功 |
| A11 | 分享及撤銷 | 唯讀脫敏快照；撤銷後不可存取；無法反查私人對話 |
| A12 | 其他 session 猜到 tripId | 讀寫皆拒絕，不洩漏內容 |
| A13 | 惡意外部內容要求改指令 | 不突破工具 allowlist、鎖定與寫入確認邊界 |
| A14 | 用量額度耗盡 | 停止新模型執行；現有行程仍可讀取與刪除 |

測試分三層：domain unit tests 驗證規則與費用；真實 PostgreSQL integration tests 驗證交易、並行與冪等；browser E2E 使用固定模型回應驗證整條互動。另用真實模型跑固定情境，記錄完成率、延遲、工具次數與成本，不用固定回應測試冒充真模型表現。

## 10. 分階段開發與交付

本節是依賴順序與驗收路線，不是完成證明；逐項實作及驗證見 [Implementation Plan](../plans/2026-09-19-dive-trip-agent.md)。技術回歸與真模型任務品質須分別驗收。

| 階段 | 可驗收交付 | 依赖 | 對應驗收 |
|---|---|---|---|
| M1 資料與 domain | 精選目錄格式、費用計算、鎖定與結構驗證，純函式測試 | 無 | A2、A4、A5 |
| M2 持久化與版本 | 匿名所有權、不可變版本、提案交易、復原與冪等 | M1 | A6、A7、A8、A12 |
| M3 互動工作台 | 對話／卡片／地圖／預算、差異確認、接續；固定模型 adapter | M2 | A1、A3、A8、A10 |
| M4 真實 Agent | 模型 adapter、有限工具、真實執行事件、錯誤／用量限制 | M3 | A1、A9、A13、A14 |
| M5 分享與公開防護 | 脫敏快照、撤銷、保存期限、刪除與費用防線 | M4 | A11、A12、A14 |
| M6 展示與發布 | 真實來源核對、授權素材、三組 demo、影片、案例頁及部署驗收 | M5 | A1–A14 |

三組可重設的 demo 為：一般規劃、鎖住宿但預算不足、查詢失敗／費用待確認。重設只能影響目前展示 session，不清除其他使用者資料。

作品案例頁說明本人貢獻、系統界線、示範資料、架構、測試及失敗處理；影片展示完整操作，但不能取代公開 demo。沒有通過 M6 前不宣稱已上線或可正式接單處理真實預訂。

## 11. 審閱與後續

人數／天數、匿名保存期限、工具上限與分享快照語義是產品約束；設計文件不攜帶 session 授權。真模型入口須另行明確、有界授權，先查核本機不可刪的原始歷史與 quota；公開部署與付費服務另有驗收及啟用門檻。

目前核心回答採 strict AnswerPlan、服務端 compiler 與 AcceptedAnswer，詳見 [回答契約](../../model-adapter.md)。數值與呈現安全不證明真模型理解、選擇或來源品質；不得用離線 vectors 或早期局部通過解除 [發布缺口](../../release-evidence.md)。
